# Problem lifecycle

Every `problem.md` has a `status` in its front matter. It moves forward
like this:

```text
Suggested ──> Researching ──> Ready to build ──> Being built ──> Solved ──> Handed over
     │              │                │                 │
     └──────────────┴────────────────┴─────────────────┴──> Paused (with a reason)
```

| Status (`status:` value) | Meaning | To move on you need |
|---|---|---|
| **Suggested** (`suggested`) | The target is on the map. Nobody is working on it yet. All 169 targets start here. | Someone volunteers to research it. |
| **Researching** (`researching`) | We are learning: what exists, who is affected, what data there is. | "What already exists", "What solved looks like" and "Data we can use" filled in; a gap statement; ideally a problem owner. |
| **Ready to build** (`ready-to-build`) | One buildable piece is scoped, with clear success criteria. | A solution folder from the template, and tasks for the first version. |
| **Being built** (`being-built`) | Code, data pipelines or designs are in progress. | A working version tested against the success criteria, ideally with the problem owner. |
| **Solved** (`solved`) | The solution works for its users and is measured against the UN indicator(s) where possible. | A plan for who runs and maintains it. |
| **Handed over** (`handed-over`) | The problem owner or another long-term home runs it. We keep the record. | - |
| **Paused** (`paused`) | Work stopped. Add `paused_reason: "..."` to the front matter (for example "no data access", "no problem owner", "out of scope"). | A reason to restart. |

## Priority

`priority` is our view of where effort is most needed: `high`, `medium`,
`low` or `unassessed`.

The starting value is derived from the UN's own 2026 progress assessment
(*The Sustainable Development Goals Report 2026*, "SDG progress by target",
pp.44-45), stored in `un_progress_2026`:

| UN assessment | Starting priority |
|---|---|
| Regression, Stagnation | `high` |
| Marginal progress | `medium` |
| Moderate progress, On track | `low` |
| Insufficient data | `unassessed` |

People may change `priority` with a reason in the pull request (for example
"a strong problem owner is ready"). `un_progress_2026` itself is UN data and
is regenerated by the tools; do not edit it by hand.

## Who changes the status?

The problem lead (or a maintainer) changes it in a pull request, then runs
`python tools/build_index.py` so the README tables update.
